Презентация о claude-kit — framework для AI-driven разработки на базе Claude Code. Цель: показать архитектуру pipeline и обосновать пилот в одной из команд. Источники: CLAUDE.md:1, README.md:12.

Проблема: хаос AI-coding

  • Один промпт превращается в код без планирования
  • Нет ревью и тестов перед merge
  • Каждый запуск даёт разный результат
  • Контекст модели загрязняется предыдущими шагами
AI-разработка сегодня ведётся ad-hoc: один промпт, сразу код, сразу коммит. Это приводит к невоспроизводимости и накопленному техдолгу. Контраст со claude-kit pipeline далее. Источник для сравнения: CLAUDE.md:1-15.

Bias и отсутствие аудита

  • Модель сама пишет план и сама его одобряет
  • Переходы между этапами не отслеживаются
  • Нет типизированных контрактов между фазами
  • Невозможно вернуться к промежуточному состоянию
Когда одна модель пишет и ревьюит — возникает creation-history bias. Нет audit-trail. Источники: .claude/PROJECT-KNOWLEDGE.md:201 (Commands shared vs Agents clean), .claude/skills/workflow-protocols/orchestration-core.md:65.

Commands видят историю задачи, agents — нет. Это исключает creation-history bias: ревьюер судит по артефакту, не по тому, как он создавался. Источники: .claude/rules/workflow.md:3-16, .claude/PROJECT-KNOWLEDGE.md:201.

Phase 0.7 Designer — SDD

  • Активируется на L/XL задачах
  • Spec как источник истины
  • 2–3 альтернативы с pros и cons
  • User approval gate перед planner
Spec-driven development: всё начинается со spec'а, не с кода
Designer запускается до planner на L/XL задачах. Производит approved spec — выбранный подход, альтернативы, acceptance criteria. Без spec'а planner может уйти в сторону. Источники: .claude/commands/designer.md, .claude/skills/workflow-protocols/orchestration-core.md:52-55.

Phase 1 Planner

  • Ресерч кодовой базы (Grep, Glob, code-researcher агент)
  • Sequential Thinking на L/XL
  • Полный план: Scope, Architecture, Tests, AC, Parts
  • Полные code examples, не сигнатуры
Planner делает ресерч и пишет детальный план с полными примерами кода. Для L/XL используется Sequential Thinking MCP. Структура плана фиксирована: ## Scope, ## Architecture, ## Tests, ## Acceptance Criteria, ## Parts. Источники: .claude/commands/planner.md, .claude/skills/planner-rules/SKILL.md:51-55.

Phase 2 Plan Review — clean context

  • Запускается как изолированный agent
  • Не видит истории создания плана
  • Verdict: APPROVED / NEEDS_CHANGES / REJECTED
  • Max 3 итерации plan-review cycle
Plan-reviewer — native Claude Code agent в чистом контексте. Получает план и типизированный handoff, возвращает verdict. Не знает, как planner создавал план — судит по артефакту. Источники: .claude/agents/plan-reviewer.md, .claude/PROJECT-KNOWLEDGE.md:217.

Iron Law: NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
Iron Law TDD: нет production-кода без падающего теста первым. Red-Green-Refactor — стандартный цикл. Spec-check на Phase 3.5 проверяет соответствие плану. Источники: .claude/skills/tdd-rules/SKILL.md:14-29, .claude/skills/workflow-protocols/orchestration-core.md:62.

Phase 4 Code Review — clean context

  • Native agent в worktree-изоляции
  • Видит только committed diff
  • Verdict: APPROVED / APPROVED_WITH_COMMENTS / CHANGES_REQUESTED
  • Max 3 итерации code-review cycle
Code-reviewer запускается в git worktree — видит только закоммиченные изменения, не историю работы coder'а. Категории issues: blocker, major, minor, nit. Источники: .claude/agents/code-reviewer.md, .claude/skills/workflow-protocols/orchestration-core.md:63-66.

Verdict state machine

stateDiagram-v2
    [*] --> Review
    Review --> APPROVED: code OK
    Review --> APPROVED_WITH_COMMENTS: minor issues
    Review --> CHANGES_REQUESTED: major issues
    Review --> NEEDS_CHANGES: plan issues
    Review --> REJECTED: scope wrong
    APPROVED --> [*]
    APPROVED_WITH_COMMENTS --> [*]
    CHANGES_REQUESTED --> Review: iter N+1
    NEEDS_CHANGES --> Review: iter N+1
    REJECTED --> [*]
Structured verdict: APPROVED и APPROVED_WITH_COMMENTS — done; NEEDS_CHANGES и CHANGES_REQUESTED — loop to previous phase (max 3); REJECTED — стоп с user intervention. Routing определяется verdict'ом автоматически orchestrator'ом. Источник: .claude/skills/workflow-protocols/orchestration-core.md:58-66.
